# Content Factory: архитектура (v2, 25.10.2026, после кросс-модельного ревью `research/critique.md`)

Источники: `research/oss-landscape.md` (рынок), `research/postiz-backend.md` (Postiz по коду v2.25.3),
`research/critique.md` (кросс-модельное ревью), опыт наших рабочих конвейеров автопостинга.

## Что это
Одна установка на много организаций (фонды, компании). Люди скидывают фото, видео, голосовые в Telegram-бот
или по ссылке. Фабрика складывает всё в одно место, AI по инструкциям организации отбирает материал,
монтирует рилсы и сторис, пишет тексты в голосе бренда, ставит в расписание и публикует во все каналы.
Владелец видит план и ленту в простой админке, участник управляет своим из бота.

## Решение по бэкенду публикации
**Postiz (v2.25.3+) как основной publisher за адаптером, прямые адаптеры там, где Postiz слаб.**
- Postiz даёт: OAuth и хранение аккаунтов, календарь и UI для людей, 30+ сетей, org на компанию,
  Public API + MCP. У нас он уже работает в проде с десятками каналов.
- Прямые адаптеры остаются: Telegram (полный журнал message_id, правка и удаление, свой бот на организацию),
  Meta для FB Reels и FB Stories (Postiz шлёт видео в `/videos`, а не `/video_reels`).
- Адаптер `Publisher` с одним контрактом, чтобы при нужде заменить Postiz на TryPost.

Отвергнуто: (а) свой планировщик и OAuth всех сетей с нуля: это переписать Postiz. (б) Только Postiz без
своего сервиса: нет приёма материала, AI, политики, ограниченных ролей для волонтёров, идемпотентности.
(в) TryPost основным: моложе, один API-ключ на workspace только у админа; держим запасным.

## Принципы v2 (из ревью)
1. **Фабрика единственный владелец плана.** Postiz не держит отложенных публикаций: в момент слота фабрика
   проверяет политику (шабат, апрув, лимиты) и вызывает Postiz "опубликовать сейчас". UI Postiz для
   операторов, расхождения видны в журнале. Так Temporal не проспит шабат и не выпустит старый текст.
2. **Граница организации везде.** `tenant_id` обязателен во всех сущностях, членство с ролями, контекст
   задаётся ботом организации или явным выбором; ключи Postiz и соцсетей только у publisher.
3. **Агент в песочнице.** Каждый прогон куратора в отдельном процессе-песочнице (как `team.py`): read-only
   входы одного tenant, своя временная папка, без ключей и общего дома, инструменты узкими командами по
   asset id. Текст людей это данные, результат агента повторно проверяется детерминированно.
4. **Предложение отдельно от допуска.** Факты только с происхождением (из заметки, транскрипта, прошлых
   постов), неизвестное не выдумывается. После рендера QA: ffprobe (кодеки, длительность, размеры), safe
   areas, лимиты текста и вложений, текст внутри сторис. Новый tenant или шаблон стартует с апрувом в боте,
   автопубликация включается после подтверждённого качества.
5. **Журнал, который переживает сбой.** Outbox с delivery id до HTTP-вызова, состояния
   submitting → accepted → published | failed | unknown, сверка по расписанию, webhook только ускоряет.
   Потерянный ответ даёт `unknown` и оповещение, а не повторный POST.

## Модель данных
- **Tenant** (организация): slug, языки (контент, отчёты, участники), timezone, brand kit (лого, шрифты,
  цвета, стиль субтитров), `policy.md` (голос, запреты, приватность, хэштеги), правила расписания
  (лимиты в день по типам, интервал, рабочие часы, blackout: шабат по закату, праздники), правила апрува
  (авто / нужен апрув для типов, например донат-посты).
- **Channel**: tenant, тип (fb_page, ig, tg_channel, yt, tiktok, linkedin), publisher (postiz|meta|telegram),
  внешние id, ссылка на секрет. Голос канала (`voice`: напр. "просто от лица табора" для TG-канала табора).
- **Contributor**: Telegram user id → tenant(ы), роль (sender, editor), язык обращения.
- **Asset**: оригинал (приватно), метаданные, транскрипт, от кого, заметка-пожелание, согласие.
- **Event**: контекст, который координатор задаёт заранее ("заїзд Пліч-о-пліч 19-23.10"), к нему
  привязываются материалы; при неясности бот задаёт один вопрос до генерации.
- **Batch**: материалы одного tenant и события; сначала идемпотентно сохраняется update и файл, бот
  подтверждает приём, таймер тишины только закрывает уже определённую группу, поздние файлы дополняют её.
- **Slot**: что, когда; derivatives, тексты по каналам, версия (апрув привязан к версии, правка сбрасывает).
- **Delivery**: slot × channel со своим статусом и попытками (частичная публикация видна по каналам).
- **Part**: каждый message_id альбома, каждый id сторис, ссылки, правки, удаление.
- **Consent**: у asset флаг согласия и ограничения (только канал табора, без лиц и т.п.), допуск учитывает его;
  производные публичны только на время публикации.

## Компоненты
1. **Ingress.** Telegram-бот на организацию или общий с маршрутизацией по contributor (aiogram +
   локальный `telegram-bot-api`: снимает лимит 20 МБ до 2 ГБ). Веб-ссылка для загрузки. Адаптер для
   своих источников (например, существующий бот команды или Telegram user-session).
2. **Store.** Оригиналы приватно (диск или S3-совместимое), производные с публичным URL на время
   публикации (нужно IG и Postiz), чистка после выхода.
3. **Curator.** Агентный прогон на батч: headless Claude (запасной Codex) с `policy.md` организации,
   набором инструментов (prep-media, talking-reel, montage-пресеты из clip-engine, транскрипция) и
   строгой JSON-схемой результата. Предлагает слоты, сам ничего не публикует.
4. **Planner.** Проверяет политику детерминированно (лимиты, интервалы, часы, blackout, дубли), кладёт
   слоты в план или в очередь апрува.
5. **Publisher.** Адаптеры postiz / meta / telegram. Идемпотентность через fence (`publish_claims` из
   clip-engine): зависший "sending" не повторяется вслепую, сверка по факту. Шабат-гейт и перед
   публикацией, и при создании задания в Postiz.
6. **Admin.** Веб: организации, каналы, участники, входящие, план (лента по дням), апрув/правка/отмена,
   журнал. Для участников то же в боте: "план", "зміни текст", "зніми".
7. **Notify.** Сводки владельцу и тем, кто прислал, на их языке.

## Стек
Python 3.12, FastAPI + Jinja/htmx админка (без SPA), SQLite WAL с миграциями (одна БД, один хост),
два контура: быстрый publish/сверка (дедлайны) и ограниченный пул media/AI-задач с lease, heartbeat,
timeout и квотами на tenant. Docker compose. Возможности провайдеров по каждому каналу tenant подтверждаются
smoke-тестом и хранятся в матрице; без подтверждения тип поста для канала выключен. Медиа: ffmpeg, Pillow, faster-whisper/Groq.
Лицензия репо MIT (Postiz отдельно, AGPL, мы его не модифицируем, ходим по API).

## Поставка open source
Чистая установка по README без моего окружения: упакованные media-команды, версионированная схема
tenant-конфига с валидацией, пример tenant без секретов. Свои боты и user-session это
необязательные адаптеры. Postiz подключается по URL и ключу. Критерий: второй tenant проходит полный цикл
на чистой машине.

## Postiz отдельным треком
Срочное закрытие уязвимостей обеих установок (2.21.10 → 2.25.3) отдельно от продукта: бэкап и проверка
восстановления на копии, апгрейд, ротация API-ключей организаций и OAuth-секретов, проверка рестарта
перед публикацией. Боевые установки с клиентскими каналами только вместе с их владельцем.
