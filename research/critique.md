# Дефекты архитектуры Content Factory

Проверены [архитектура](../ARCHITECTURE.md), [контракт задачи](TASK.md), [ландшафт](oss-landscape.md) и [разбор Postiz](postiz-backend.md). Ниже дефекты проекта решения, по убыванию серьёзности. Упомянутые риски Postiz взяты из предоставленного исследования; эксплуатация и runtime-проверки не выполнялись.

1. **P0. Граница tenant не определена для входящих материалов, команд и внешних ключей.**

   **Проблема.** Contributor может состоять в нескольких организациях, но общий бот маршрутизирует только по contributor. У Asset, Batch, Slot и Publication не заданы обязательный tenant и ограничения связей. Нет модели доступа владельца в вебе и проверки права участника менять конкретный материал. Фраза "org на компанию" не задаёт проверяемую связь `tenant → Postiz instance → org → key → integrations`. Исследование отдельно предупреждает о широких правах API-ключа и обходе ограничений USER в self-host ([Postiz, §2 и §4](postiz-backend.md)).

   **Почему важно.** Один человек может прислать материал сразу двум фондам; неверный контекст отправит фото, уведомление или команду удаления в чужую организацию. Предположение о безопасности Postiz UI не закрывает доступ к нему ограниченных участников.

   **Исправление.** Ввести tenant-bound membership с ролями и проверкой авторства; обязательный `tenant_id` во всех сущностях и составные ограничения на связанные записи. Контекст организации выбирать через привязанного бота или явный выбор в общем боте. Upload-ссылки делать ограниченными по tenant, сроку и правам. Все команды, скачивания и jobs проверять на backend. Ключи Postiz держать только у publisher, сверять принадлежность integration; ограниченным участникам не выдавать Postiz UI до исправления и отрицательных проверок permissions.

2. **P0. Headless-агент обрабатывает недоверенные данные без описанной песочницы.**

   **Проблема.** Curator получает подписи, голосовые, транскрипты и инструменты монтажа, но архитектура задаёт только JSON-схему и запрет "сам ничего не публикует". Не заданы доступы процесса к файловой системе, сети, credentials и материалам других tenants ([архитектура, компоненты 1 и 3](../ARCHITECTURE.md#компоненты)).

   **Почему важно.** Инструкция в подписи или транскрипте может заставить агента вызвать инструмент с чужим путём, прочитать секреты или отправить исходник наружу. Валидный JSON результата не ограничивает побочные действия, уже выполненные агентом.

   **Исправление.** Запускать каждое задание в изолированном процессе/контейнере с read-only входами одного tenant и отдельной временной папкой. Не передавать publisher credentials, общий домашний каталог и произвольный shell. Инструменты выдавать через узкие команды с проверкой asset ID, путей и параметров; сеть ограничить необходимыми сервисами. Считать весь пользовательский текст данными, а результат агента проверять повторно перед сохранением и публикацией.

3. **P1. Два независимых календаря позволяют обойти политику, апрув и шабат-паузу.**

   **Проблема.** Фабрика владеет Planner/Admin, а Postiz одновременно предлагается как календарь и UI для людей. Проверка при создании задания не контролирует дальнейшее выполнение Temporal. Исследование прямо указывает, что workflow спит до даты публикации и собственного шабат-гейта не имеет ([Postiz, §6, п.5](postiz-backend.md)). Не определено, что происходит после изменения текста, политики, времени или повторной попытки.

   **Почему важно.** Пользователь может переставить публикацию через Postiz, а задержанный workflow или retry попасть в запрещённое окно. Апрув прежнего текста может остаться действительным после его замены.

   **Исправление.** Сделать фабрику единственным местом изменения плана; Postiz UI оставить операторским инструментом с контролем расхождений. Апрув привязать к версии текста, медиа и списку назначений, изменение сбрасывает апрув. До использования автономного расписания Postiz обеспечить проверку актуальной политики непосредственно перед внешней отправкой и каждым retry в его publishing activity. Без такой доработки строгую паузу оставлять на контролируемых прямых адаптерах, а не считать её обеспеченной внешним admission gate.

4. **P1. Fence не решает потерю ответа и не обнаруживает незапущенный workflow.**

   **Проблема.** В архитектуре есть "sending" и "сверка по факту", но нет протокола сверки. Postiz не принимает публичный idempotency key, каждый повторный POST создаёт записи, а HTTP success возможен даже при ошибке запуска workflow ([Postiz, §2 и §6, п.3](postiz-backend.md)).

   **Почему важно.** После таймаута неизвестно, создан ли пост, а его Postiz ID может быть потерян. Повтор даст дубль, вечный fence даст пропуск. Успешный create без работающего workflow оставит контент навсегда в расписании.

   **Исправление.** До HTTP-вызова сохранять durable outbox и попытку с уникальным factory delivery ID, tenant, payload hash и временем. Разделить состояния `submitting`, `accepted`, `unknown`, `published`, `failed`. Периодически сверять сохранённые Postiz IDs со state/error/releaseId; webhook использовать как ускоритель, а не единственный источник. Для потерянного ID предусмотреть однозначную корреляцию, подтверждённую контрактом API; при её отсутствии переводить в `unknown` с оповещением и ручным разбором, без повторного POST. Задать срок обнаружения зависшего задания.

5. **P1. Один статус Slot скрывает частичные публикации, а журнал не сможет выполнить "зніми".**

   **Проблема.** Slot содержит несколько каналов, один статус и один ID задания Postiz. Publication обещает ID каждой части, хотя исследование показывает один итоговый ID для серии IG/FB Stories. Прямой Meta заявлен только для FB Reels/Stories. Кроме того, DELETE Postiz удаляет группу заданий и не удаляет уже вышедшие объекты в соцсетях ([Postiz, §2 и §3](postiz-backend.md)).

   **Почему важно.** TG может выйти, IG упасть, а часть сторис опубликоваться. Общий retry продублирует успешные назначения. Команда участника "сними" может затронуть соседнее задание или оставить публичные копии без сообщения об этом.

   **Исправление.** Отделить редакционный Slot от Delivery на каждый канал/формат, с собственными версиями, попытками и статусами; статус Slot вычислять из Delivery. Хранить ID каждой внешней части. Сохранить прямой адаптер и для IG Stories, пока Postiz не отдаёт полный ledger. Разделить операции отмены расписания, удаления опубликованного и правки; явно хранить возможности провайдера и показывать неподдерживаемые операции как требующие ручного действия. Повторять только неуспешные Delivery.

6. **P1. Приватность заканчивается на оригинале, а согласие не участвует в допуске к публикации.**

   **Проблема.** Asset имеет поле "согласие", но Planner не проверяет его и не описывает отзыв. Производные получают публичный URL и удаляются "после выхода", без учёта нескольких каналов, отложенного скачивания, retries и копий в Postiz. Его local media storage публичен ([Postiz, §2 и §4](postiz-backend.md)).

   **Почему важно.** Фото детей или подопечных могут оказаться доступны ещё до апрува. Чистка после первого успешного канала сломает остальные; чистка только в фабрике оставит копию в Postiz. Отозванное согласие не остановит уже созданные задания.

   **Исправление.** Хранить оригиналы и непубликуемые производные в private object storage. Согласие/разрешение моделировать как проверяемый допуск с областью использования и происхождением, неизвестный статус направлять на апрув. Выдавать производные только на этапе передачи publisher через ограниченный publishing URL. Задать retention для каждой копии и удалять по завершении всех зависимых Delivery с запасом на скачивание. Отзыв должен блокировать новые отправки, отменять ожидающие и создавать задачи удаления уже вышедших копий.

7. **P1. Поддержка провайдера принята за готовность автопубликовать всем организациям.**

   **Проблема.** Фазы заканчиваются переходом каналов за 1-2 дня, но не содержат допуска developer apps и проверки конкретных аккаунтов. Исследование требует Meta permissions для сторонних компаний, TikTok audit для публичного Direct Post и LinkedIn scopes; `UPLOAD` TikTok требует ручного завершения, Stories доступны не любому IG account ([Postiz, §3](postiz-backend.md)).

   **Почему важно.** Сервис примет фотографии и покажет расписание, но не выполнит цель "на всех каналах". Общий OAuth приложения также создаёт общий отказ при отзыве permissions, который нельзя исправить новым tenant-файлом.

   **Исправление.** Добавить обязательный onboarding канала со статусом готовности, проверкой scopes, типа аккаунта, срока токена и фактической тестовой публикацией нужного формата. Для TikTok проверять именно публичный `DIRECT_POST`. Не включать неподтверждённое назначение в автоматический план, сообщать владельцу причину и действие для восстановления. Получение approvals вынести в отдельную зависимость запуска; срок разработки не считать сроком допуска платформами.

8. **P1. JSON-схема и policy.md не обеспечивают ни достоверность, ни качество готового контента.**

   **Проблема.** Curator сразу предлагает слоты, Planner проверяет расписание и дубли. Нет проверки фактов, связи утверждений с исходниками, просмотра результата монтажа и проверки медиа по назначению. Между тем исследования фиксируют разные ограничения Stories, Reels, каруселей и Shorts; Postiz upload validation не равен требованиям соцсети ([ландшафт, §2 и §4](oss-landscape.md), [Postiz, §2 и §3](postiz-backend.md)).

   **Почему важно.** Из фотографий нельзя достоверно получить имя, событие, сумму сбора или согласие. Технически валидный слот может содержать выдуманный факт, неверные субтитры, обрезанные лица или Story без текста, который остался только в caption.

   **Исправление.** Разделить предложение и допуск. Требовать происхождение фактических утверждений, неизвестные данные не выдумывать. После рендера проверять длительность, геометрию, кодеки, звук, safe areas, лимиты текста/вложений и наличие текста внутри Story. При низкой уверенности, чувствительной теме или неизвестных фактах отправлять владельцу превью и один конкретный вопрос. Новые tenant/шаблоны запускать с апрувом до подтверждения качества на реальных материалах.

9. **P1. Единственный общий воркер связывает долгий монтаж с дедлайнами публикации всех tenants.**

   **Проблема.** Один воркер должен закрывать батчи, запускать headless-агентов, транскрибировать, рендерить и публиковать. Нет очереди с восстановлением, приоритетов, таймаутов и лимитов на организацию. Локальный Bot API при этом допускает большие входящие файлы ([архитектура, стек и Ingress](../ARCHITECTURE.md), [ландшафт, §3.1](oss-landscape.md)).

   **Почему важно.** Один длинный ролик или зависший CLI задержит публикации и обработку отмен у всех организаций. Перезапуск между этапами может потерять работу; поток одного tenant исчерпает диск или вычислительный бюджет остальных.

   **Исправление.** Сохранить монолит, но отделить короткие deadline-sensitive операции отправки/сверки от ограниченного пула media/AI subprocesses. Задания хранить в БД с lease, heartbeat, timeout и восстановлением после рестарта. Ввести лимиты входящего объёма, диска, длительности и AI-бюджета на tenant, справедливый выбор задач и оповещение о просрочке. Для v1 выбрать одну поддерживаемую БД с миграциями вместо необоснованного обещания "Postgres по флагу".

10. **P1. Batch по тишине не определяет событие и не гарантирует сохранность присланного.**

    **Проблема.** Не задан ключ группировки Batch, обработка Telegram media groups, повторных updates и поздних файлов. Таймер тишины не отличает два события одного отправителя или одно событие нескольких волонтёров. Нет подтверждения, что оригиналы уже сохранены, и простого пути исправления ошибочного объединения ([архитектура, модель и Ingress](../ARCHITECTURE.md)).

    **Почему важно.** Люди будут повторно отправлять материал при отсутствии ответа, а фабрика смешает разные поездки или выпустит один сюжет несколько раз. Требование "просто прислать фото" останется зависимым от ручного разбирательства оператора.

    **Исправление.** Привязать поток загрузки к tenant и контексту события/кампании, который координатор задаёт заранее. Сначала идемпотентно сохранить update, автора, принадлежность media group и файл; затем подтвердить приём и показать статус. Использовать таймер только для закрытия уже определённой группы, предусмотреть позднее дополнение, разделение и объединение в простом интерфейсе. При неоднозначном контексте задавать один вопрос до генерации, а не угадывать событие.

11. **P1. План апгрейда не включает восстановление и последствия уже существовавших уязвимостей.**

    **Проблема.** Фаза 0 сводится к обновлению staging и smoke-test; защита второго уязвимого инстанса отложена до переноса клиентской установки. Пропущены восстановление двух БД и uploads, сохранение Temporal state/workflow versions, ротация слабых старых ключей и связь JWT_SECRET с шифрованием данных. Всё это явно перечислено в исследовании ([Postiz, §1 и §5](postiz-backend.md)).

    **Почему важно.** Апгрейд не отзывает ранее утёкшие или предсказуемые credentials. Обычный откат образа поверх изменённой схемы либо смена JWT_SECRET может сделать подключённые аккаунты недоступными. Отказ инфраструктуры остановит сразу все организации, а не один бот.

    **Исправление.** Отделить срочное закрытие уязвимостей обеих установок от миграции продукта. Зафиксировать проверенные версии приложения и orchestrator, снять полный backup и проверить restore на копии, затем пройти upgrade с сохранением workflow state. После обновления заменить старые org API keys/OAuth secrets по runbook; ротацию JWT_SECRET выполнять отдельно с учётом encrypted данных. До перевода tenants проверить рестарт перед публикацией, backup/restore, reconnect и оповещения о застрявших Delivery, измерить ресурсный бюджет на реальной нагрузке.

12. **P2. Переиспользуемый продукт зависит от неописанного личного окружения автора.**

    **Проблема.** План переносит `TASK-INTAKE`, montage-пресеты, `publish_claims`, `team-tool` и legacy user-session, но не определяет публичную поставку и границы этих зависимостей. Новый tenant описан как "один tenant-файл", хотя нужны аккаунты, секреты, участники, brand assets и runtime агентов. В контракте требуется open-source библиотека/сервис для повторного использования ([TASK](TASK.md), [архитектура, компоненты и фазы](../ARCHITECTURE.md)).

    **Почему важно.** Публичный GitHub сам по себе не даст второй организации запустить систему без домашних каталогов Pavel, личных CLI-сессий и приватных скриптов. Команде из 1-2 человек придётся сопровождать персональные интеграции как обязательную часть продукта.

    **Исправление.** Определить минимальную воспроизводимую поставку с упакованными media-командами, версионированной схемой tenant-конфига, проверкой обязательных параметров и примером без секретов. Личные `team-tool`/user-session оставить необязательными ingress-адаптерами; внешний Postiz подключать по URL и ключу, не требовать разворачивать весь стек для любого режима. Проверка готовности OSS: чистая установка по README и полный цикл второго tenant без доступа к личному окружению и материалам первого.
