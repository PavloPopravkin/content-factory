## 1. Что берём как есть

1. **Солнечный расчёт** `src/content_factory/solar.py:7-26`. NOAA, refraction 90.833°, UTC с переходом даты, `None` в полярных широтах. Для Чикаго (lon -87.6) минуты заката переходят за 24:00 UTC, это учтено (`solar.py:25-26`).
2. **Окно шабата** `planner.py:17-41` (`blackout_violations`). Берёт пятницу по локальной дате, проверяет соседние недели (-7, 0, +7), закрывается при `None` (`planner.py:35-37`, fail-closed). Формат правил `weekly` и `sunset_shabbat` (`config.py:24-51`).
3. **Движок допуска** `planner.py:44-81` (`admit`). Чистая функция slot + tenant + история → список нарушений: лимиты в день, интервал по реальному времени (DST-безопасно, `planner.py:59-64`), рабочие часы, blackout, capability канала, апрув текущей версии. Без I/O, легко вызывать из любого слоя.
4. **Апрув по хешу** `storage.py:160-204`. Хеш caption + kind + конфиг каналов + метаданные медиа, сброс при расхождении (`check_approval`, `storage.py:171-184`), защита от гонки через `BEGIN IMMEDIATE` (`storage.py:195-199`). Это ровно то, что нужно для "Женя одобряет каждый пост": одобрил байты, правка сбрасывает.
5. **Журнал доставки** (migrations/002_recovery.sql:8-25, `scheduler.py:64-184`). Fence `UNIQUE (tenant_slug, slot_id, channel_id)` (002:22), состояния submitting → accepted → published | failed | unknown | deferred (`models.py:18-24`), `unknown` вместо слепого повтора (`scheduler.py:68-70`, `173-177`), checkpoint каждого внешнего ID, повторная проверка политики перед каждым HTTP (`send_gate`, `scheduler.py:113-124`).
6. **Сверка Postiz** `publishers/postiz.py:68-92`. Маппинг `QUEUE/PENDING/PROCESSING/PUBLISHED/ERROR` → наши состояния, `releaseId` как доказательство публикации.
7. **Прямые адаптеры**: Meta для FB Reels через `/video_reels` (`publishers/meta.py:73`, `109`), потому что Postiz шлёт FB-видео в `/videos` (ARCHITECTURE.md:17); Telegram с полным ledger message_id (ARCHITECTURE.md:16).
8. **Конфиг tenant** с валидацией (`config.py:103-151`): timezone IANA, policy.md внутри папки tenant, языки, brand. Схема пригодна как "настройки организации" независимо от того, где они редактируются.

## 2. Что конфликтует с новым направлением

### 2.1 Инвариант "план владеет только фабрика, Postiz исполняет сейчас"
Где: MANIFEST.md:12, DECISIONS.md "Postiz исполнителем за своим сервисом" (отвергнуто (г) "отложенные посты внутри Postiz"), ARCHITECTURE.md:25-27, код `postiz.py:57` (`"type": "now"`).
Конфликт: если админка и календарь в Postiz, человек ставит пост в календарь Postiz, и план живёт в БД Postiz. Причина прошлого запрета не исчезла: Temporal-workflow спит до `publishDate`, паузы по закату в нём нет (research/postiz-backend.md:106). Значит, перенос плана в Postiz без гейта внутри Postiz нарушает шабат и апрув.
Варианты:
- (A) Оставить план в фабрике, Postiz только "сейчас". Тогда админка вне Postiz, это противоречит слову Pavel'я.
- (B) Двусторонняя синхронизация планов. Две точки истины, класс багов "REPLACE vs append", отвергаю.
- **(C, рекомендую) План в Postiz, гейт в Postiz.** Единственная точка истины плана = Postiz DB. Перед каждой отправкой workflow Postiz вызывает активность `admission` (наш policy + journal сервис, fail-closed: сервис недоступен → отложить, не публиковать). Наш `admit`, `blackout_violations`, апрув по хешу и fence переезжают за этот вызов без переписывания логики.
Цена (C): нужна правка Postiz (см. 2.3), новая версия workflow (workflows версионированы: `post.workflow.v1.1.2.ts`, research/postiz-backend.md:95, 164).

### 2.2 Non-goal "SPA-админка; хватит FastAPI + htmx"
Где: MANIFEST.md:43, ARCHITECTURE.md:79.
Конфликт: админка = Postiz (Next.js). Свой htmx-UI больше не строим. Non-goal надо перевернуть: "не строим свою админку; всё, что видит оператор, живёт в Postiz".

### 2.3 "Мы его не модифицируем, ходим по API"
Где: ARCHITECTURE.md:83.
Конфликт: Pavel хочет, чтобы Postiz реализовал бот и админку. Без форка Postiz не даст: гейт перед отправкой, состояние "ждёт апрува владельца", роль "только загрузка" (её нет, research/postiz-backend.md:86), свой бот на организацию (один `TELEGRAM_TOKEN` на установку, research/postiz-backend.md:79).
Следствия форка:
- AGPL-3.0: изменённый Postiz, доступный пользователям по сети, обязан отдавать им исходник (§13). Для продажи это допустимо, но форк публичный. Наш Python-сервис остаётся отдельным процессом за HTTP, его MIT не заражается (на уровне "отдельная программа"; юридически не проверено).
- Стоимость rebase на каждый релиз Postiz. Держать patch-набор узким: (1) активность admission в workflow, (2) статус/кнопки апрува, (3) страница настроек организации (политика, шабат, лимиты), (4) вкладка "входящие из бота". Остальное через Public API и MCP (research/postiz-backend.md:168, `start.mcp.ts`).
- Риск в правах: при отсутствии `STRIPE_PUBLISHABLE_KEY` `PermissionsService.check()` пропускает запросы до проверки ADMIN (research/postiz-backend.md:87). На живой установке этой переменной нет. Значит, до выдачи аккаунтов Жене и волонтёрам нужен deny-тест и фикс владеющего слоя. Runtime-эксплуатация не проверялась.

### 2.4 Целевая архитектура "Postiz как исполнитель за адаптером Publisher"
Где: MANIFEST.md:38, DECISIONS.md "Postiz исполнителем...".
Конфликт: роли меняются местами. Postiz теперь платформа, фабрика его сервис политики, журнала, AI-куратора и бота. Адаптер `Publisher` (`publishers/base.py`) остаётся для прямых путей (Meta Reels, Telegram), но перестаёт быть центром.

### 2.5 Шабат опционален в схеме
Где: `config.py:59` (`blackout: list[Blackout] = Field(default_factory=list)`), живой пример `tenants/demo/tenant.yaml:26` (`blackout: []`), поля отступов `config.py:47-48` с `ge=0`.
Конфликт с жёстким правилом: шабат обязателен в любой автоматике. Сейчас tenant может его выключить. Правка класса: шабат = свойство платформы, не opt-in tenant. Минимумы из глобального правила: до заката пятницы ≥30 мин, после заката субботы ≥40+30=70 мин. `margin_before_min >= 30`, `margin_after_min >= 70` как валидатор; пустой blackout → ошибка конфигурации на старте (fail-fast).
Открытый вопрос: чей закат. Для WWG (Чикаго) Женя и аудитория в Чикаго, Pavel сейчас в Испании (глобальный CLAUDE.md, раздел "Шабат"). Консервативно: объединение окон по координатам tenant и по координатам оператора. Решает Pavel.

### 2.6 Accepted-до-blackout становится главным риском
DEBT.md:6-7: задание, принятое Postiz до окна, может уйти позже. При модели (C) запланированный пост и так лежит в Temporal. Значит, гейт обязан стоять в момент реальной отправки внутри workflow, а не при создании поста. Проверка при создании нужна только как UX-подсказка.

### 2.7 Апрув без личности
`storage.py:186` `approve(self, tenant, slot_id)` не знает, кто одобрил, через какой канал (бот, Postiz UI) и на какой версии превью. Для "Женя одобряет каждый пост" и для продажи нужен актор, роль, канал апрува и журнал. Таблиц membership/contributor нет (DEBT.md:12, критика 1 в research/critique.md:7-11).

### 2.8 Ключи соцсетей "только у publisher"
MANIFEST.md:13. В модели (C) токены FB/IG живут в БД Postiz (env `FACEBOOK_*`, `INSTAGRAM_*` на живой установке). Прямой Meta-адаптер для FB Reels требует второй токен той же страницы → две точки хранения одного секрета. Варианты: патч FB-провайдера Postiz на `/video_reels` (тогда прямой адаптер не нужен) или явный trade-off в DEBT. Рекомендую патч провайдера: это одна функция, и он закрывает класс "Postiz слаб на формате X" внутри платформы.

### 2.9 Модель каналов и типов
`config.py:85` типы каналов: нет Google Business Profile, который нужен WWG. Есть ли GBP-провайдер в Postiz v2.25.3 и через какой ключ, **не проверено** (в research/postiz-backend.md провайдер не разобран). `models.py:7-10` `Kind` без явного carousel (вычисляется из числа медиа, `planner.py:72`) и без text-only поста.

### 2.10 Хранилище и масштаб
SQLite WAL, один хост (ARCHITECTURE.md:79), tick вызывается CLI по tenant (`cli.py:140`, `scheduler.py:53`), без демона. Для admission-сервиса, который синхронно зовёт Temporal-активность, нужен долгоживущий HTTP-процесс. SQLite допустим на одном хосте, но журнал станет на критическом пути публикаций всех организаций. Решение по БД (свой Postgres рядом или отдельная схема) отложить до прототипа; в `postiz-postgres` на проде сейчас ничего не писать.
Открытые P2 из ревью (DEBT.md:15-22): N+1 в `history()/slots()` (8) станет реальным, когда admission вызывается на каждый пост всех организаций; сервисная проверка tenant (11) обязательна, как только появится HTTP-вход.

## 3. Бот как в YourHelp
Сейчас в ядре нет ни приёма, ни бота (DEBT.md:12, ARCHITECTURE.md:61-63 описан, не реализован). Telegram-провайдер Postiz только публикует, один бот на установку, разговорного режима нет (research/postiz-backend.md:79). Значит, "Postiz реализует бот" в буквальном смысле = новый сервис рядом с Postiz (или app в его монорепо), который:
- ведёт диалог и принимает медиа (опыт `~/www/yourhelp/autopost/intake`, `@croscor_bot`),
- пишет черновики в Postiz через Public API / MCP в организацию tenant,
- присылает владельцу превью и кнопки "одобрить / править / снять", кнопка вызывает тот же апрув по хешу.
Какой из двух путей (отдельный сервис за API или app внутри форка) выбрать, зависит от того, насколько глубоко Postiz-админка должна показывать диалоги. Рекомендую отдельный сервис за API + вкладка "входящие" в форке, это держит patch-набор малым.
