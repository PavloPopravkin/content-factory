## 0. Суть в пяти строках

1. Postiz остаётся **немодифицированным** v2.25.3+ (обновляется тегом upstream). Он отвечает за OAuth каналов, хранение токенов, календарь для оператора, превью `/p/[id]` с комментариями и саму отправку в FB/IG/YouTube/TikTok.
2. **content-factory = sidecar-сервис**, единственный владелец плана, апрува, шабата, фактов, журнала, приёма материала и Telegram-диалога. В Postiz он кладёт посты только как `DRAFT` и переводит их в `now` в момент слота после проверки политики.
3. Пока пост в `DRAFT`, Temporal-workflow не запущен (`posts.service.ts:964-966`), значит "спать мимо шабата" нечему. Это главный механизм безопасности без форка.
4. Люди (Женя, Иванка, волонтёры служения) работают **в Telegram**, не в Postiz. Аккаунты Postiz получают только операторы. Клиенту показывается превью Postiz по ссылке.
5. "Админка в Postiz" без форка = пункт меню и панель, встроенные через уже существующий на S2 прокси-инжектор (`postiz-fanout.service`, `postiz-live.md` п.6), страницы отдаёт sidecar. Если Pavel хочет "настоящую" вкладку в коде Postiz, это переход на угол "тонкий форк" (раздел 11), не этот дизайн.

## 3. Модель данных sidecar

Хранилище: остаётся SQLite WAL на старте (одна машина, один процесс записи, `cf-core-fit.md` §2.10). Переход на собственный Postgres (не `postiz-postgres`: Postiz делает `prisma db push` на старте, `postiz-code.md` §(e)) при втором коммерческом клиенте или при появлении второго процесса записи.

```
tenant(slug PK, kind ENUM('ministry','charity','commerce'), display_name, timezone IANA,
       lat, lon, languages[], postiz_instance, postiz_org_id, postiz_key_ref,
       approval_mode ENUM('none','owner'), facts_ref, pack_ref, status)
member(id, tg_user_id, display_name, lang)
membership(member_id, tenant_slug, role ENUM('contributor','approver','admin'),
           UNIQUE(member_id, tenant_slug, role))
channel(tenant_slug, channel_id, kind ENUM('fb','ig','gbp','tg','yt','tiktok'),
        route ENUM('postiz','direct'), postiz_integration_id, caps JSON)
asset(id, tenant_slug, sha256 UNIQUE per tenant, origin ENUM('bot','archive','social_import'),
      contributor_id, taken_at, kind, w, h, duration, consent ENUM('ok','faces_ok','no_faces','unknown'),
      flags JSON, path)
slot(tenant_slug, slot_id, kind ENUM('post','carousel','reel','story','text','offer'),
     at_utc, status, version, content_hash, curator_run_id)
slot_content(tenant_slug, slot_id, version, channel_id, text, media JSON, extras JSON)
approval(tenant_slug, slot_id, content_hash, actor_member_id, via ENUM('bot','admin','grant'),
         decided ENUM('approved','rejected'), ts)            -- append-only
postiz_map(tenant_slug, slot_id, channel_id, version, postiz_post_id, postiz_group, state)
delivery(...)                                                -- как сейчас, 002_recovery.sql
event(ts, tenant_slug, actor, type, payload)                 -- аудит, append-only
```

Отличия от phase-1:
- `tenant.kind` задаёт только дефолты (служение и фонд: `approval_mode=none` разрешён, как решил Pavel для фонда 21.10 и 25.10 (`yourhelp-system.md:11`); коммерция: `owner` обязателен, валидатор не даст `none`).
- Шабат не поле тенанта, а свойство платформы (§6).
- `approval` записывает актора и канал. Апрув `grant by Pavel` из autopost (`wwg-tenant.md:9`) импортируется как `via='grant'`.
- `consent` у медиа: для служения и фонда правило "лица детей можно, имена и истории нельзя" (`yourhelp-system.md:90`); для WWG "без лиц клиентов, без адресов" (`wwg-tenant.md:47`). Куратор обязан проставить поле, код проверяет, что `unknown` не уходит в слот.

## 4. Telegram-бот: UX и маршрутизация

### 4.1 Транспорт
Остаётся текущая проверенная схема @croscor_bot: Server 1 принимает вебхук, `inbox.py` тянет очередь, `guard.py` проверяет слова, смотритель участника без ключей вызывает `team-tool social ...`, `team_outbox.py` исполняет с правами участника (`yourhelp-system.md:66-70`). Меняется только одна точка: маршрут `team_outbox.py:36-39, 90-109` по полю `social` в `team.json` ведёт в `factory-api` вместо `social.py` / `engine.py`. Для участника ничего не меняется: те же команды `send|plan|now|cancel|text|approve|preview`.

Встроенный Telegram Postiz для диалога не используется: один глобальный `TELEGRAM_TOKEN` и `getUpdates` (`telegram.provider.ts:19, 85-130`), это несовместимо с вебхуком @croscor_bot. Если нужен постинг в каналы через Postiz, под него заводится отдельный бот-паблишер. Рекомендация: каналы Telegram публиковать прямым адаптером (полный журнал message_id по глобальному правилу), Postiz для Telegram не подключать вообще.

### 4.2 Мульти-тенант
- `membership` определяет, куда идёт файл. Одна роль в одном тенанте: файл сразу туда.
- Несколько тенантов (Pavel, будущие волонтёры служения и фонда): бот отвечает inline-кнопками "Куда: YourHelp / YourCamp / Служение / WWG". Выбор запоминается на пачку (тишина 45 мин, как в `run.sh`), не навсегда.
- Тенант без membership у участника отклоняется на уровне `factory-api` (сервисная проверка тенанта, DEBT P2 №11 в `cf-core-fit.md:74`), а не только в боте.

### 4.3 Что сохраняем из UX YourHelp
По фактам использования (`yourhelp-system.md`, раздел про Иванку): ответ "прийнято N файлів", сводка после сборки на языке участника, список "Попереду N". `cancel` и `text` у фонда не использовались, их оставляем, но не выносим в первый экран.

### 4.4 Карточка апрува для Жени
Паттерн из `wilshawdirect/telegram-ops-kit` (MIT, `github-analogs.md` п.4) и уже работающий в `engine.py:141-153, 450-471`:

```
WWG · пт 06.11 10:00 Chicago · рилс · FB + IG
[медиа-группа: обложка + 1-3 кадра или само видео]
Текст IG: ...
Текст FB: ...
GBP: не идёт (видео)
Превью как в ленте: https://postiz.../p/<id>   [не проверено для DRAFT]
Версия a3f9c1
[Одобрить] [Править текст] [Заменить фото] [Перенести] [Снять]
```

Правила карточки:
- В `callback_data` nonce + `content_hash`; нажатие на устаревшую версию отвечает "карточка устарела, вот новая".
- Повторное нажатие идемпотентно. Срок жизни карточки = время слота.
- "Править текст" открывает диалог со смотрителем Жени; любая правка меняет хеш и снимает апрув (`storage.py:171-184`).
- Неодобренный к сроку коммерческий слот не публикуется, получает `expired`, Жене одна строка "не вышло, нет ок". Никакой публикации "по умолчанию".
- Напоминание: одно за 3 часа до слота, вне шабата.

### 4.5 Сводки
- Ежедневная (фонд, служение): как `last-summary-ua.txt` сейчас.
- Еженедельная Жене (WWG): охват из Postiz analytics + заявки с `utm_campaign` из lead-engine. Канал @wwgwow_bot (`wwg-tenant.md` §6). Отправка автоматическая, значит тоже под шабат-гардом.

## 5. Куратор (AI)

- **Исполнитель:** headless Claude по пакету тенанта (как `run.sh` + `TASK-INTAKE.md`), `--allowedTools` только файловые и скрипты медиа, без сети к соцсетям и без ключей. Плательщик по тенанту (`payer: yevhen` для WWG держит лимит 70%, глобальный CLAUDE.md).
- **Пакет тенанта** `tenants/<slug>/`: `tenant.yaml`, `TASK-PLAN.md` (отбор и тексты), `voice.md`, `facts.json` (для WWG ссылка на `approved-business-facts.json`), `rules.md` (визуальные запреты).
- **Контракт вывода:** строгий JSON-план (идея из `n8n-ai-newsroom`, `github-analogs.md` п.3), валидатор pydantic. Невалидный JSON = сборка не принята, участнику "не собрал, разбираюсь".
- **Код проверяет то, что сейчас проверяет только промпт** (`yourhelp-system.md`, "Что зашито под фонд": лимиты дня проверяет только куратор):
  - лимиты в день, интервалы, окно часов, шабат: `admit` (`planner.py:44-81`);
  - фразы-запреты из `facts.json` (`"200+ reviews"`, `"bonded"`, `"99.99%"` и т.д., `wwg-tenant.md:17-18`): детерминированный lint текста;
  - числа: в тексте WWG любое число должно совпадать со списком разрешённых значений; число отзывов не ставить, пока Женя не ответит (`wwg-tenant.md:12`);
  - донат-посты фонда автоматом не уходят (`autopost.py:303`) и становятся `approval_mode=owner` для этого слота;
  - `consent != unknown` у каждого медиа.
- **Куратор никогда не публикует** и не создаёт посты в Postiz. Он пишет план, sidecar создаёт DRAFT.
- **Встроенный агент Postiz** (Mastra, `gpt-5.2` в коде, `load.tools.service.ts:116`) не используется: он не знает шабат и апрув, а `IntegrationSchedulePostTool` ставит пост в расписание. Держим его выключенным отсутствием `OPENAI_API_KEY` [проверить на живом env, `github-analogs.md` вопрос 3]. MCP-токены Postiz никому не выдаём.

## 6. Политика: шабат, апрув, лимиты. Где стоит каждый слой

### 6.1 Шабат как свойство платформы
- Окно = объединение окон по координатам тенанта и по координатам оператора (сейчас Испания, `steward.py:94-100`). Для WWG это Чикаго ∪ Испания; для фонда Киев ∪ Испания.
- Отступы: минимум 30 мин до заката пятницы, 40+30 = 70 мин после заката субботы (глобальное правило). Валидатор `margin_before_min >= 30`, `margin_after_min >= 70`; пустой или выключенный blackout = ошибка на старте (`config.py:59` и `tenants/demo/tenant.yaml:26` сейчас это разрешают, `cf-core-fit.md` §2.5).
- Неизвестный закат = закрыто (`planner.py:35-37`).
- **Время на отправку.** Пост, отправленный до окна, может дойти после (resumable upload рилса длится минуты, `wwg-tenant.md:91`). Правило: `send_deadline = window_start - lead(kind)`, где lead = 15 мин для фото, 60 мин для видео. Это закрывает DEBT "accepted до blackout" (`cf-core-fit.md` §2.6). По этому правилу слот `WWG-1106-sink` (пт 06.11 10:00 Chicago при окне с 10:28) был бы запрещён: это решение Pavel'я, сейчас этот слот в autopost, не в фабрике.
- Фонд переходит с фиксированного окна "пт 15:00 - сб 21:00 Киев" (`autopost.py:289-296`) на платформенное. Летом новое окно шире на 1-1.5 ч (`yourhelp-system.md:110`), публикаций станет меньше в субботу вечером, это ожидаемо.
- Одна реализация. `steward.in_shabbat`, `autopost.py:shabbat_now`, ADS `publish.py:96-108` и `solar.py` сводятся к одному модулю; остальные движки импортируют его, пока живут (одна точка истины на concern).

### 6.2 Слои (fail-closed каждый)

| # | Слой | Где | Что ловит |
|---|---|---|---|
| 1 | план | `admit` при приёме плана куратора | слот в окне, лимиты, без апрува для коммерции |
| 2 | send_gate | перед каждым HTTP к Postiz или каналу (`scheduler.py:113-124`) | правило изменилось, апрув снят, окно наступило |
| 3 | DRAFT-only | в Postiz пост живёт только как DRAFT до команды `now` | Temporal не спит мимо шабата, потому что workflow не запущен (`posts.service.ts:964-966`) |
| 4 | sweeper | каждые 60 с `GET /public/v1/posts` по каждому org: пост в `QUEUE`, не созданный командой `now` фабрики, с датой в окне или без апрува → `PUT /posts/:id/status` в draft (`posts.service.ts:1384-1407`) + алерт Pavel'ю | человек поставил пост в календарь Postiz руками; MCP или CLI обошли фабрику |
| 5 | доступ | аккаунты Postiz только операторам, регистрация закрыта (`DISABLE_REGISTRATION`), агент и MCP выключены | уменьшает число путей, которые должен ловить слой 4 |

Слабое место слоя 4: человек может поставить `now` прямо в UI, и sweeper этого не поймает (пост уходит сразу). В sidecar-угле это закрывается только слоем 5, то есть доверием к операторам. Если это неприемлемо, нужен guard в `postSocialInternal` (`post.activity.ts:331`), это уже форк (раздел 11). Честно: **без форка шабат гарантирован для всего, что идёт через фабрику, и для отложенных постов людей; для `now` вручную оператором в шабат гарантии нет.**

Ещё одно [не проверено]: меняет ли `PUT status → draft` уже спящий workflow. По коду `startWorkflow` гасит запущенные workflow поста (`posts.service.ts:937`), но для changePostStatus путь нужно проверить на стенде. Это первый тест фазы 2.

### 6.3 Апрув
- Коммерция: апрув владельца на точный `content_hash` версии. Хеш включает текст по каналам, медиа sha256, тип и время слота.
- Фонд и служение: `approval_mode=none` по решению Pavel'я, но донат-посты и посты с новыми лицами детей переводятся в `owner` (approver = Pavel).
- Апрув живёт только в sidecar. Комментарии в превью Postiz (`public.controller.ts:54-90`) читаются sidecar-ом и пересылаются Жене или куратору как правки, но апрувом не считаются.

## 8. "Админка внутри Postiz" без форка

Что уже даёт немодифицированный Postiz оператору:

- Превью `/p/[id]` и комментарии к фрагментам текста.
- Ошибки публикаций, аналитика каналов.

Что добавляет sidecar:
- Пути `/factory/*` на том же домене. Caddy (`croscor-infra.caddy:34`) направляет их в `factory-api`. Страницы: "Входящие из бота", "Очередь апрува", "Медиатека тенанта", "Политика тенанта" (только чтение настроек и окна шабата на 4 недели вперёд), "Журнал доставок".
- Пункт меню "Factory" в интерфейсе Postiz через тот же HTML-инжект, что уже делает `postiz-fanout.service` (`fanout_server.py`, :8912) для массового добавления FB-страниц. Код этого сервиса не читан, файлы только root (`postiz-live.md` п.6) [не проверено].
- Авторизация страниц: sidecar проверяет сессию Postiz, вызывая бэкенд Postiz с cookie запроса, и берёт org из ответа [не проверено: имя cookie и эндпоинт "текущий пользователь"]. Если это не выйдет надёжно, страницы закрываются собственным входом через Telegram Login для операторов.

Честная оценка: это "внутри Postiz" для глаз оператора, но не в коде Postiz. Пользователь видит один домен и одно меню. Инжект ломается, когда upstream меняет разметку меню; страхуем тестом после каждого обновления тега (скриншот + проверка наличия пункта).

## 9. Безопасность и изоляция тенантов

### 9.1 Postiz
- Deny-тест обхода прав без `STRIPE_PUBLISHABLE_KEY` (`permissions.service.ts:49-61`) на стенде до выдачи любого аккаунта не-Pavel'ю. Sidecar-угол не выдаёт аккаунты Жене и волонтёрам, поэтому риск ограничен операторами.
- Секреты из `docker-compose.yml` (0644) в `.env` под vault (`inv-protect`), дефолтный пароль temporal заменить (`postiz-live.md` п.8). Это правка прода, только с апрувом и по `call-guard`-подобной проверке, что ничего не публикуется в момент рестарта.
- Регулярный бэкап `postiz-postgres` (сейчас только ручной снимок 25.10, `postiz-live.md` п.7).
- Подписка на GitHub advisories upstream, обновление тега в течение 72 ч после critical.
- Агент `/agents` и MCP: выключены, проверка в фазе 1.

### 9.2 Sidecar
- Ключ Postiz на организацию (Public API ключ org), в vault, ссылка `postiz_key_ref`. Вызов в org A ключом org B невозможен на уровне Postiz; sidecar дополнительно проверяет `tenant_slug` из membership на каждом входе.
- Куратор и смотрители без ключей (как сейчас, `team.py:1-8`), все действия через фиксированный набор команд.
- Входящие слова участника через `guard.py` (как сейчас). Медиа из бота: проверка MIME по содержимому, лимит размера, перекодирование до попадания в план.
- Журнал `event` append-only, реплика в бэкап ежедневно.

### 9.3 Коммерция
- Отдельный инстанс Postiz "commerce" для клиентов за деньги (WWG и следующие). Служение и фонды Pavel'я остаются на текущем `postiz.croscor.com`. Это прямой ответ на довод записи 04.11 "токены всех клиентов в одной системе". Цена: ещё ~0.8 ГБ RAM на S2 (`postiz-live.md` п.8) или отдельный VPS.
- Компромисс: WWG первым живёт на текущем инстансе в своей org, второй инстанс поднимается при первом внешнем платящем клиенте. Решение Pavel'я.

## 10. Коммерческая упаковка и AGPL

- Немодифицированный Postiz как сервис: §13 AGPL не срабатывает (он о модифицированных версиях), уведомления сохраняем, ссылку на upstream-исходник держим в футере (`postiz-code.md` §g).
- Инжект JS в страницы Postiz: юридически серая зона "модифицировали ли мы интерфейс". Безопасный вариант: исходник инжект-скрипта публикуем открыто под AGPL, он маленький и без логики. Логика sidecar остаётся закрытой отдельной программой за HTTP [юридически не проверено].
- Бренд Postiz продавать нельзя, white-label без форка невозможен (логотип захардкожен, `(preview)/p/[id]/page.tsx:63`). Значит в sidecar-угле **продукт для клиента = Telegram-бот + карточки апрува + наши страницы `/factory/*` + отчёт**, а Postiz = операторская консоль за кадром. Клиент Postiz не видит, кроме превью по ссылке (на нём логотип Postiz; для коммерции превью можно генерировать своё из `slot_content`).
- Упаковка: "Контент-служба" по подписке: N постов в неделю, апрув в Telegram, GBP + FB + IG, еженедельный отчёт с заявками. Для служения и благотворительности та же система бесплатно или по себестоимости.
- Лицензии зависимостей (Polotno, CopilotKit) нас не касаются, пока клиенты не работают в UI Postiz.

## 15. Риски

1. **Ручной `now` оператора в шабат** не ловится без форка (§6.2). Митигация: только Pavel имеет аккаунт; иначе форк из одного коммита.
2. **Sweeper как единственная защита от ручного планирования.** Упал sweeper, кто-то запланировал пост, пост ушёл. Митигация: health-алерт при пропуске 3 тиков; аккаунты только операторам.
3. **Поведение `changePostStatus` над спящим workflow** не проверено (§6.2). Если не гасит, sweeper бесполезен, остаётся только доступ. Проверка первым делом в фазе 2.
4. **Инжект меню** ломается на обновлениях upstream (300 коммитов в месяц, `postiz-code.md` §f). Митигация: тест после смены тега; страницы `/factory/*` работают и без меню.
5. **Двойной FB-токен** (Postiz + прямой Reels). Ротация в одном месте забудется. Митигация: page-токен выводится из одного `META_ACCESS_TOKEN` в рантайме, в Postiz своё OAuth-подключение; алерт при 190-й ошибке.
6. **GBP через прямой OAuth Pavel'я** уже висит в ADS (`unknown` с 03.11). Без выяснения класса ошибки тот же сбой придёт в WWG.
7. **Один инстанс Postiz на всех** до коммерческого разделения повторяет довод записи 04.11.
8. **Миграция фонда меняет окно шабата** (летом публикаций в субботу вечером не будет). Это правильно, но меняет привычный ритм.
9. **Нагрузка на подписку Жени** от куратора WWG (лимит 70%).
10. **Postiz Public API лимит** `API_LIMIT=30` [единица не проверена, `postiz-live.md` п.10]. Sweeper по нескольким org каждые 60 с может упереться. Митигация: интервал по числу org, вебхуки Postiz только как ускорение.
11. **Три движка ещё 4-6 недель.** Пока они живут, шабат и дубли считаются в трёх местах. Митигация: общий модуль шабата импортируют все три уже в фазе 3.
